# Política de revisión de hallazgos de SonarQube

Contrato para resolver issues de SonarQube en este repositorio. Aplica tanto a Claude Code como a cualquier persona del equipo que corrija issues de Sonar.

## 1. Alcance permitido (lo único que se puede tocar)

- Solo se aplican cambios que correspondan a un **issue concreto reportado por SonarQube** (Code Smell, Bug, Vulnerability, Security Hotspot o Duplication), citando la regla exacta (ej. `python:S1172`, `python:S3776`, etc.).
- Cambios típicos permitidos: reducir complejidad ciclomática, eliminar código muerto/no usado, renombrar variables poco claras, eliminar duplicación, corregir *code smells* de estilo, ajustar manejo de recursos (context managers, cierres de archivos/conexiones), simplificar condicionales sin cambiar su resultado lógico.
- Nada que no tenga un issue asociado se toca, aunque "de paso" se vea algo mejorable.

## 2. Prohibiciones explícitas

- **Nunca modificar lógica de negocio**: reglas de cálculo, condiciones que afecten el resultado, validaciones de negocio, umbrales, flujos de decisión.
- **Nunca cambiar el comportamiento observable**: mismo input debe producir el mismo output antes y después del cambio.
- **Nunca modificar firmas públicas** (funciones, endpoints, contratos de request/response) sin aprobación explícita del usuario.
- **Nunca alterar tests para que "pasen"** ocultando el problema real (cambiar aserciones, comentar tests que fallan, aumentar timeouts para maquillar un fallo).
- **Nunca tocar configuración de infraestructura/despliegue** (CI/CD, variables de entorno, Dockerfiles) salvo que el issue sea explícitamente sobre eso.
- **No borrar código "por sospecha de no uso"** sin verificar referencias reales en todo el repo.

## 3. Zona gris — detenerse y preguntar antes de aplicar

Hay reglas de Sonar que *parecen* de estilo pero pueden cambiar comportamiento. Requieren aprobación explícita antes de aplicarse:

- Cambios en manejo de excepciones (`try/except`, tipos de excepción capturados).
- Cambios en comparaciones (identidad vs igualdad, coerciones de tipo).
- Reordenar condiciones con evaluación de cortocircuito.
- Cualquier "Security Hotspot" que implique cambiar validación de entradas o lógica de autenticación/autorización.
- Cualquier refactor que cruce más de un módulo o límites de capas (ej. de endpoint a service).

## 4. Cuándo NO modificar código (issues cosméticos sin impacto funcional)

Si el hallazgo es puramente de estilo/convención (ej. naming conventions, nombres en español, longitud de comentarios) y corregirlo:

- no aporta ningún beneficio funcional, y
- requiere tocar código que funciona intencionalmente así (ej. nombres elegidos a propósito, documentados en el propio código), o implica un cambio innecesariamente amplio (muchos callers, muchos archivos),

→ no modificar el código. En su lugar, indicar cómo silenciarlo desde la interfaz de SonarQube (marcar como "Won't Fix" / "False Positive") o ajustando la configuración del análisis de Sonar (`sonar-project.properties`, exclusiones de reglas en el pipeline), explicando el motivo.

## 5. Proceso de trabajo obligatorio

1. Un issue de SonarQube = un cambio, en un commit separado y descriptivo (`fix(sonar): S1172 - remove unused parameter in X`).
2. Ejecutar los tests existentes **antes y después** de cada cambio. Si no hay tests para ese código, avisar antes de tocarlo.
3. Trabajar siempre en una rama separada (nunca directo a `main`); el usuario revisa el diff antes de mergear.
4. Documentar cada cambio: regla resuelta, archivo, línea, y una frase de qué se hizo.
5. Además del commit, agregar siempre una entrada breve en la sección de patrones recurrentes del repo correspondiente (6/6.1/6.2/…), **aunque el hallazgo aparezca por primera vez** — no esperar a que se repita. El objetivo es ir construyendo un registro que ayude a evitar reintroducir el mismo tipo de issue al escribir código nuevo. Si el repo todavía no tiene su propia subsección, crear una nueva siguiendo el mismo formato que las existentes.

## 6. Patrones recurrentes en este repo (para no reincidir al escribir código nuevo)

Registro de hallazgos de Sonar resueltos en este repo — **cada issue se documenta acá desde la primera vez que aparece**, no solo cuando se repite (ver sección 5, paso 5) — para evitarlos proactivamente al escribir código nuevo, no solo al corregir el issue existente:

- **`python:S1481` (variable local no usada)**: al desempaquetar una tupla (`a, b = funcion()`) cuando solo una parte del resultado se usa después, renombrar la parte no usada a `_` (convención estándar de Python para descartar un valor), no dejarle un nombre real sin leer. Ejemplo: `confirmar_redistribucion` en `src/endpoints/pedidos/redistribucion/endpoints_core.py` — `_, estado_confirmado = await asyncio.to_thread(_db_procesar_sap_redistribucion, ...)` (commit `115af3f`, PR 573, 2026-09-13). Al escribir un `await asyncio.to_thread(...)` nuevo que devuelve una tupla, revisar de entrada qué partes del resultado realmente se leen más abajo.
- **`S1192` (literales de string duplicados)**: cuando un mismo literal se repite 3+ veces en un archivo —típicamente nombres de tarea de Celery (`'src.tasks.mod.func'`) usados a la vez en `beat_schedule` y `task_routes`, nombres de cola, permisos (`target_permission=`), títulos de sección en emails, o claves de configuración—, extraerlo a una constante a nivel de módulo (o de clase, si ya hay un patrón `_LABEL_`/`_SECCION_` establecido en el archivo, ver `src/utils/email_notifier.py`) desde el primer commit. Ejemplos: `src/celery_app.py` (`TASK_RECONCILIAR_TRANSFERENCIAS_PENDIENTES`), `src/endpoints/pedidos/redistribucion/_notifications.py` (`_PERMISO_ODCSAP_VIEW`), `src/utils/email_notifier.py` (`_SECCION_ACCION_RECOMENDADA`).
- Al agregar una tarea nueva a `beat_schedule`/`task_routes`, un `target_permission` nuevo en notificaciones, o una sección de email reutilizada, revisar si el literal ya se repite en el mismo archivo antes de copiar/pegar el string.
- **`S3776` (complejidad cognitiva > 15)**: aparece sobre todo en funciones que procesan una colección con un `for` y, dentro, un `if/elif/else` con varias ramas (ej. clasificar la respuesta de un envío a SAP en éxito/encolado/error/pendiente-de-confirmar) o una validación con múltiples pasos secuenciales que pueden abortar temprano. Patrón de fix usado en este repo: extraer el cuerpo de UNA iteración (o un paso autocontenido de la validación) a un método privado `_verbo_sustantivo(...)` que reciba los datos necesarios y, si el original mutaba contadores/listas compartidos, seguir mutándolos por referencia (dict/list) para no cambiar el comportamiento; el método/función que queda arriba pasa a ser un simple `for`/secuencia de `if` de aborto temprano que delega. La extracción de lógica a un método NO cuenta contra la complejidad del llamador (solo las estructuras de control SÍ), así que casi siempre alcanza con extraer el bloque más anidado. Ejemplos: `_procesar_envio_itr_nuevo` (extraído de `_enviar_itrs_a_sap`), `_construir_lineas_producto_mba`/`_construir_linea_producto_consolidado` (extraídos de los exportadores MBA), o el conjunto de 5 helpers extraídos de `crear_solicitudes_transferencia_desde_pedido` (ver commit `ba4ae23`). Al escribir una función nueva con más de 2 niveles de anidamiento (`for`→`if`→`if`) o más de 3-4 ramas `if/elif/else`, considerar extraer el cuerpo interno a un helper desde el diseño inicial, no esperar a que Sonar lo marque.

Si se detecta un patrón nuevo que se repite en más de un issue, agregarlo a esta lista con el archivo/ejemplo donde se resolvió, para que sirva de referencia al escribir código similar en el futuro.

## 6.1 Patrones recurrentes en scnexus-front (frontend Vue 3 + TS + Tailwind)

Hallazgos específicos del análisis de Sonar sobre `web-scnexus` (repo `scnexus-front`), detectados al resolver 56 issues del módulo `mba3-consultas` (PR 397, 2026-08-31). Igual que en la sección 6, evitarlos proactivamente al escribir código nuevo:

- **Falso positivo de `S1135` ("TODO" comment) en comentarios en español**: la regla busca la subcadena literal `todo` sin distinguir mayúsculas ni límites de palabra, así que matchea falsamente palabras españolas como "**todo**s los filtros...", "necesitan **todo** el ancho...". Antes de tocar código por este issue, leer el comentario completo: si no hay una tarea pendiente real, marcar el issue como **False Positive** vía API/UI con ese motivo, no editar el comentario.
- **Falso positivo de `Web:ItemTagNotWithinContainerTagCheck`/reglas de estructura HTML similares cuando el elemento vive dentro de un componente de librería** (ej. `<li>` dentro de `<ComboboxOptions>` de `@headlessui/vue`): el analizador estático de Sonar solo ve el `<template>` fuente, no el HTML que el componente renderiza en runtime (que sí es válido, ej. un `<ul>` real). Verificar qué renderiza el componente antes de "corregir" la estructura — si ya es válida en runtime, marcar **False Positive**.
- **`Web:S6845` (tabindex en elemento no interactivo) sobre un contenedor scrolleable**: `tabindex="0"` en un `<div>`/`<section>` con `overflow-x:auto` para que el teclado pueda desplazarlo es el patrón WAI-ARIA estándar de "región desplazable" (scrollable region), no un error. Marcar **Won't Fix** citando ese patrón; no quitar el `tabindex`.
- **`Web:S6819` ("usa `<button>`/`<section>`/`<dialog>` en vez del rol ARIA") sobre un elemento con rol simulado anidado dentro de otro elemento interactivo real**: HTML no permite `<button>` dentro de `<button>`. Cuando el elemento con rol simulado (ej. `<span role="button">`) vive dentro de un `<button>` real, la regla no se puede aplicar tal cual sin reestructurar: convertir el contenedor exterior a `<div role="button" tabindex="0" @keydown.enter/.space="...">` y el interior a un `<button>` real (ver `AppDateFilterInput.vue`, commit del fix `Web:S6819,MouseEventWithoutKeyboardEquivalentCheck`).
- **`Web:S6819` sobre `role="dialog"` manual (modal con backdrop propio + focus-trap propio + `@keydown.esc`)**: patrón establecido en 7+ componentes del proyecto (`UploadErrorModal.vue`, `CorregirSkuModal.vue`, `BuscarSkuModal.vue`, etc.) antes de esta migración. El fix correcto es migrar a `<dialog>` nativo con `showModal()`/`close()`, `@cancel.prevent` (reemplaza `@keydown.esc`, preservando cualquier confirmación previa al cierre), detección de backdrop-click vía `evento.target === elDialog` en un `@click` sobre el propio `<dialog>` (reemplaza el wrapper manual + `@click.self`), y elimina el focus-trap manual (`showModal()` ya lo hace nativamente). El `::backdrop` no es alcanzable con CSS `scoped` de Vue — usar un `<style>` sin scoped con una clase específica. Ver `UploadErrorModal.vue` como implementación de referencia. **Al crear un modal nuevo, usar `<dialog>` nativo desde el diseño inicial, no `role="dialog"` manual.**
- **`typescript:S6606` (`||` → `??`) y en general cualquier cambio de operador de coerción**: antes de aplicar el fix automático, verificar si el operando izquierdo puede ser un valor falsy-no-nulo válido (`''`, `0`, `false`). Si puede serlo, es un cambio de comportamiento real (zona gris, sección 3) — requiere decisión explícita del usuario sobre qué comportamiento es el correcto, no aplicar a ciegas.
- **Componentes Vue que envuelven un `<input>`/control nativo en un `<div>` contenedor (ej. `AppDateInput.vue`, `DebouncedSearchField.vue`)**: si no exponen una prop `id` explícita que se reenvíe al control interno, un `<label for="...">` en el componente padre no puede asociarse correctamente (el *fallthrough* automático de atributos de Vue cae en el `<div>` contenedor, no en el control real) → dispara `Web:S6853`. Al crear un componente que envuelve un control nativo, agregar `id?: string` a sus props y enlazarlo al control interno desde el diseño inicial.
- **El número de línea que reporta Sonar puede no apuntar a la función correcta** cuando dos funciones están una junto a la otra y el reporte se generó antes de otros fixes en el mismo archivo (los fixes previos corren líneas). Antes de asumir cuál función es, localizarla por nombre/firma o por complejidad real (contar ramas), no solo por cercanía a la línea reportada — se perdió tiempo planificando un fix sobre `handleStReintentado` (trivial, ~4 de complejidad) cuando la función realmente reportada con complejidad 141 era `handleIntegrarOC`, la siguiente en el archivo (`ProcesoCompletoView.vue`).
- **`typescript:S3776` en una función `async` con efectos secundarios (llamadas a API, refs, router, toast), no en una función pura**: no se puede extraer la función completa a un módulo aparte y testear igual que una función pura. El patrón que funcionó (`useFileUpload.ts`: `processUploadError` 278→<15, `uploadFile` 122→<15, `reintentarConCorrecciones` 47→<15): (1) extraer toda la lógica de **decisión/cálculo puro** (parseo de la respuesta, armado de mensajes, clasificación de errores, decisión de qué toast mostrar) a funciones puras `(datos) => resultado` **fuera** del composable/componente, exportadas y con tests de caracterización; (2) extraer los tramos de **orquestación async** (la llamada a la API + sus ifs de control) a funciones async separadas (pueden quedar como funciones hermanas dentro del mismo `<script setup>`/composable, sin necesidad de exportarlas ni testearlas, si dependen de refs/composables del cierre); (3) la función original queda como una secuencia lineal de pasos que delega toda rama a (1) y (2). Antes de dar por buena la extracción, si dos o más funciones puras nuevas necesitan saber "¿ya se encontró algo por otra vía?" (un `if (encontrado.length === 0)` que antes leía una variable acumulada compartida), hay que pasarles ese acumulado como parámetro explícito — si no, la extracción cambia sutilmente en qué orden se resuelve la ambigüedad y puede alterar el resultado final para inputs reales (ver `processUploadError`: se detectó así una regresión real de comportamiento antes de comitear, corregida con testing diferencial contra la versión pre-refactor).
- **Un conteo manual de "ramas anidadas" NO predice de forma confiable la Cognitive Complexity real de Sonar**: en un segundo barrido sobre el mismo PR (56 issues iniciales + 4 funciones de complejidad extrema ya "reducidas a <15"), Sonar volvió a reportar 7 funciones de `useFileUpload.ts` y `handleIntegrarOC` de `ProcesoCompletoView.vue` por encima de 15 — algunas ya habían sido "arregladas" en la ronda anterior (`handleIntegrarOC` pasó de 141 a un supuesto <15, pero la siguiente ronda reportó 50). El algoritmo real pondera secuencias de operadores lógicos (`&&`/`||`/`??`), ternarios y el nivel de anidamiento de forma no obvia a simple vista, y no hay `eslint-plugin-sonarjs` ni `sonar-scanner` instalado localmente en este repo para verificar el número exacto antes de comitear. Mitigación: (1) al extraer, apuntar a dejar la función que queda muy por debajo de 15 (una secuencia casi lineal de llamadas, no "justo bajo el límite"), no confiar en un conteo manual cercano al umbral; (2) tratar cualquier "<15" de un conteo manual como una estimación, no una garantía — el siguiente análisis real de Sonar en CI es la única confirmación verdadera; (3) si Sonar vuelve a reportar la misma función tras un fix, no es un error de proceso, es la métrica real distinta de la estimada — simplemente extraer más agresivamente.
- **`Web:S6819` sobre `role="button"` NO se resuelve manteniendo el rol simulado, ni siquiera con teclado manejado a mano**: el fix de la sección anterior (`div role="button"` exterior + `button` real anidado para evitar `<button>` dentro de `<button>`) volvió a ser reportado por Sonar en la siguiente ronda — la regla rechaza *cualquier* `role="button"` sobre un elemento no nativo, sin excepción por manejo de teclado. La única forma de silenciarlo con código (no con Won't Fix) es eliminar el anidamiento de raíz: convertir el trigger y el control secundario (ej. botón de "limpiar") en **botones reales hermanos**, no anidados, moviendo el borde/fondo/foco a un `<div>` contenedor no interactivo con `focus-within:ring-*` (en vez de `focus:ring-*` en el botón). Ver `AppDateFilterInput.vue`. Evitar el atajo de un botón hermano posicionado con `absolute` + un offset en píxeles "calculado a mano" sobre el ícono decorativo — sin medir el `boundingBox()` real (vía Playwright u otra herramienta), es fácil que el ícono quede superpuesto en vez de al lado; usar flexbox con los elementos como hermanos del mismo contenedor es más robusto y no requiere ese cálculo.
- **Migrar una llamada de un método `@deprecated` (pass-through puro) a su reemplazo (ej. `mba3ConsultasService.X()` → `pedidosService.X()`)**: es un cambio mecánico y seguro en el código de producción (mismo destino final, un nivel de indirección menos), pero **rompe en silencio cualquier test que mockee el módulo/objeto viejo** (`vi.mock('.../mba3ConsultasApi', ...)`) — el mock nunca se llama, y según el assert puede fallar con un mensaje confuso ("expected to be called") en vez de señalar el mock desactualizado. Correr *solo* los tests de las funciones puras afectadas no lo detecta: hay que correr la suite completa (`npx vitest run tests/unit`) tras este tipo de cambio, no únicamente los archivos de test que uno recuerda que existen — los tests a nivel de composable (ej. `tests/unit/composables/useFileUpload.test.ts`, `usePedidoDetalle.test.ts`) mockean el servicio completo y son fáciles de pasar por alto si no se busca primero con `find`/`Grep` qué archivos importan ese composable. El fix del test es actualizar el `vi.mock` al nuevo módulo/objeto (mismo nombre de método, mismo comportamiento), no tocar la aserción de negocio.
- **Si Sonar reporta el mismo patrón de código en un solo call-site pero el archivo tiene 2+ ocurrencias idénticas** (ej. `mba3ConsultasService.getPedido(...)` repetido en `uploadFile` y en `reintentarConCorrecciones`, pero el análisis de PR solo marcó una porque solo esa línea estaba en el diff "nuevo"): una vez decidido que el fix es seguro, aplicarlo a **todas** las ocurrencias idénticas del archivo, no solo a la marcada — de lo contrario el gemelo sin tocar dispara el mismo hallazgo en la siguiente pasada de Sonar.
- **Extraer/mover código preexistente a una función nueva lo convierte en "código nuevo" del PR para el análisis de Sonar, incluso sin cambiarlo una sola línea** — un tercer barrido sobre este mismo PR encontró 12 issues nuevos que no eran del código que se acababa de escribir, sino de líneas movidas *verbatim* al extraer funciones en la ronda anterior: un `void` redundante (`S3735`) copiado tal cual desde el original, un union type duplicado (`S4323`) que ya existía dos veces en el archivo pero solo se marcó al mover una de las dos, y regex ya existentes (`[A-Za-z0-9...]` con flag `/i`, `S5869`) que llevaban tiempo con la misma redundancia sin ser evaluadas en ningún diff previo. Al planificar una extracción, no asumir que el código movido queda "gratis" solo porque no se reescribió — pasa a ser analizado de cero, y conviene revisarlo con la misma atención que código recién escrito (comprobar `||` vs `??`, ternarios anidados, regex, etc.) antes de comitear, en vez de descubrirlo en la siguiente ronda de la API de Sonar.
- **`new_duplicated_lines_density` no viene con una regla puntual como los issues normales** — hay que pedir `/api/measures/component?metricKeys=new_duplicated_lines_density` para el número total y `/api/measures/component_tree?...&strategy=leaves` para ubicar los archivos, y `/api/duplications/show?key=<archivo>` para ver los bloques exactos con su par (archivo+línea+tamaño) en el otro lado. Antes de asumir "hay que unificarlo", leer el bloque completo en AMBOS lados: el detector normaliza literales, así que dos bloques con la misma forma pero un array de columnas, un rol, o un color distintos cuentan como "duplicados" aunque codifiquen una regla de negocio real por vista — esos se dejan intactos (ver `claseResaltadoModificado` y `availableColumns` en `PedidoDetalleView.vue`/`CargarPlantillaView.vue`: mismo shape, roles/colores/columnas distintos). Solo se extrae lo que es byte-identico (o casi) en ambos lados.
- **Antes de decidir cómo extraer un bloque duplicado, verificar con grep si alguna de las dos copias es código muerto** — en `PedidoDetalleView.vue`/`CargarPlantillaView.vue`, dos funciones a nivel de archivo (`limpiarColumnasModificadasEnStorage`, `cargarColumnasModificadasDesdeStorage`) estaban duplicadas entre los dos archivos, pero **ninguna de las dos se llamaba nunca** — la lógica realmente en uso vivía duplicada *otra vez*, esta vez inline como callbacks pasados a `usePedidoDetalle(...)`, y esa versión inline tenía un comportamiento ligeramente distinto (limpiaba un ref adicional) que la función muerta. `grep -n "nombreFuncion("` para contar llamadas reales antes de extraer evita construir el composable a partir de la copia equivocada.
- **Un delegador de una línea (`function f(x) { composable.f(x) }`) casi siempre se puede reemplazar por un destructuring directo (`const { f } = composable`) sin tocar el `<template>`** — en `<script setup>`, la plantilla resuelve el identificador por nombre en el scope del setup, no le importa si viene de una función local o de un composable destructurado. Excepción: si el wrapper no es un passthrough puro (ej. le pasa un argumento adicional que el método del composable no recibía originalmente, como `confirmarRedistribucion(puedeConfirmarRedistribucion)`), hay que dejarlo como wrapper explícito — comparar la firma de ambos lados antes de colapsarlo.
- **`typescript:S3358` al construir un sufijo de texto pluralizado (ej. "1 pendiente" vs "2 pendientes") dentro de otro ternario que decide si ese sufijo aplica en absoluto**: patrón fácil de introducir al escribir un template string nuevo con singular/plural inline (`` `${n} item${n === 1 ? '' : 's'}` ``) anidado dentro de la condición que decide si mostrar el bloque completo (`n > 0 ? \`...${n === 1 ? '' : 's'}...\` : ''`). Extraer el ternario del plural a su propia variable (`const plural = n === 1 ? '' : 's'`) ANTES de interpolarlo en el string, desde el primer commit — no esperar a que Sonar lo marque en la siguiente ronda. Ejemplo: `IntegracionSAPModal.vue::calcularResumenSolicitudesTexto` (`plural`/`sufijoPendientes`, 2026-08-31).
- **`typescript:S6544` ("Promise-returning function provided to property where a void return was expected") sobre una opción `persist?: () => void` de un composable compartido, a la que se le pasa una función async fire-and-forget (ej. `persist: savePreferences`, con `savePreferences` async)**: NO envolver en un wrapper síncrono ni forzar `await`/`.catch()` en el call site si la función ya maneja sus propios errores internamente (verificar: ¿tiene su propio `try/catch`, o delega en algo que lo tiene?) — el fix correcto es ampliar el tipo de la opción compartida a `() => void | Promise<void>`, que es exactamente lo que ya se está haciendo en tiempo de ejecución (llamarla sin esperar el resultado) y evita forzar un tipo `void` incorrecto. Cambio de un solo archivo de tipos, cero impacto en runtime. Mismo patrón que el punto anterior sobre "extraer código preexistente lo marca como nuevo para Sonar": el `persist: savePreferences` ya existía idéntico en 3+ archivos antes de este hallazgo (`ExcelLikeGridView.vue`, `RedistribucionTiendas.vue`, `ProcesamientoSAPView.vue`) sin ser reportado — solo se marcó al mover el patrón a un composable nuevo (`useProductosPedidoColumnas.ts`). Ejemplo: `useColumnVisibilityToggle.ts`/`useColumnDragAndDrop.ts` (`persist`, 2026-08-31).

## 6.2 Patrones recurrentes en api-middleware-sap (.NET 8 / C#)

Hallazgos del análisis de Sonar sobre `api-middleware-sap`, PR 395 (2026-08-31). Mismo criterio que las secciones anteriores:

- **`external_roslyn:CA1859`** (cambiar el tipo de un parámetro de una interfaz de colección, ej. `IReadOnlyDictionary<K,V>`, a la clase concreta, ej. `Dictionary<K,V>`, "for improved performance" — evita la indirección de la interfaz, permite devirtualizar la llamada): **solo aplicar sin preguntar cuando el método es `private` (o `static` privado) Y tiene un único caller Y ese caller ya construye/tiene un `Dictionary` concreto** (no otra implementación de `IReadOnlyDictionary`, como `ImmutableDictionary` o `.AsReadOnly()`) — verificar los tres con `grep -n "NombreMetodo("` antes de tocar la firma. Si el método es `public`/`internal` con más de un caller, es un cambio de firma (zona gris, sección 3) que requiere confirmar que TODOS los callers ya pasan el tipo concreto. Ejemplo: `ValidatePurchaseOrderUseCase.MapItem(itemData, itemErrors)`.
- **`csharpsquid:S6960`** ("This controller has multiple responsibilities and could be split into N smaller controllers"): antes de dividir a ciegas, revisar si el controller actual existe *a propósito* como consolidación de dos controllers previos que definían la misma ruta (route collision) — si es así, confirmar con el usuario antes de reabrir esa división (ver sección 3, "cualquier refactor que cruce límites de capas/estructura"). Si se decide dividir: cada acción HTTP se mueve a su propia clase `[ApiController]` con el **mismo `[Route("api/v{version:apiVersion}/recurso")]`** en ambas — la ruta final de cada endpoint (`[HttpGet]`, `[HttpPost("accion")]`) no cambia, solo la organización en archivos; verificar que ningún verbo/ruta quede definido en más de una clase (causaría un error de arranque de ASP.NET Core por ruta duplicada). Los tests de integración que pegan por HTTP (`WebApplicationFactory`) no necesitan cambios — no referencian el nombre de la clase del controller. Ejemplo: `WarehousesController` → `WarehousesController` (GET) + `WarehousesValidationController` (POST validate), commit `92d44b6`.
